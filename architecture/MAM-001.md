## 2. Arquitectura recomendada — la más sencilla que cumple

No instalar todo a la vez. Empezar con lo mínimo, probar la comunicación, y solo añadir un componente cuando una prueba lo justifique.

### Componentes

| Componente | Para qué | Estado |
|---|---|---|

| **Vercel Board** | Coordinador de agentes y tareas persistentes. ### Por qué Board y no un bus de mensajes propio

- Un agente solo puede llevar su trabajo en un archivo Markdown, pero varios agentes necesitan reclamaciones, estado, dependencias y escalación humana sin inventar cada uno su propio almacén.
- Board es una primitiva sin interfaz, un almacén de mensajes, donde los agentes leen y escriben por CLI o SDK. Cada tablero se organiza en canales e hilos, un hilo mantiene conversación, contexto y actualizaciones juntas, y las etiquetas siguen el detalle.
- Es agnóstico al harness: Claude Code, Codex, OpenCode, eve y otros pueden colaborar como si fueran un solo harness.
- Riesgo: es experimental, anunciado el 18 de noviembre de 2026. Para un proyecto personal en fase experimental es aceptable; para producción habría que reevaluarlo.

### Alternativa si Board no convence

GitHub solo, con Issues + Pull Requests + un archivo `tasks/` en el repositorio. Es más simple, gratis, y ya cumple el registro verificable. La desventaja es que Nova, que vive en ChatGPT, no puede leer GitHub directamente sin una integración, y el intercambio tendría que pasar por Gmail o por Victor como mensajero. Board resuelve eso mejor, si Nova puede usar su CLI/SDK.

## 3. Protocolo común de mensajes

Cada mensaje, en Board, en GitHub o por Gmail, debe contener:

- Identificador único
- Agente emisor
- Agente destinatario
- Fecha y hora
- Tipo de mensaje
- Identificador de tarea
- Objetivo
- Instrucciones
- Prioridad
- Estado
- Resultado o motivo de bloqueo

### Ejemplo — instrucción de Nova a MUSE

```
Tarea: MAM-001
Emisor: Nova
Destinatario: MUSE
Tipo: Construcción
Prioridad: Alta

Objetivo: diseñar el esqueleto modular de MAMMOUTH.

Instrucciones:
1. Preparar la estructura de carpetas.
2. Documentar la arquitectura.
3. Separar los módulos para permitir ampliaciones.
4. No copiar código de la aplicación anterior de Lovable.
5. No modificar proyectos existentes.
6. No incorporar funcionalidades no autorizadas.

Entrega esperada: documentación, estructura propuesta, decisiones técnicas y pruebas realizadas.
```

### Ejemplo — respuesta de MUSE

```
Tarea: MAM-001
Estado: Completada / Parcial / Bloqueada

- Trabajo realizado.
- Archivos creados o modificados.
- Decisiones técnicas.
- Pruebas ejecutadas y resultados.
- Problemas encontrados.
- Riesgos identificados.
- Pendientes.
- Enlace a los cambios.
```

Nova deberá revisar esta entrega antes de presentarla como aprobada. Los cambios rechazados no se incorporan a producción.

## 7. Seguridad y límites

- No realizar acciones irreversibles sin autorización.
- No compartir credenciales entre agentes mediante mensajes ordinarios.
- Utilizar permisos mínimos necesarios.
- Proteger las claves API y los secretos. Las claves no van en el repositorio, ni en Gmail, ni en mensajes ordinarios.
- Registrar las operaciones importantes.
- Separar entornos experimentales y de producción.
- No enviar correos ni mensajes externos sin autorización.
- No contratar servicios ni generar gastos sin autorización.
- No modificar ni eliminar la aplicación anterior de Lovable.
- No asumir que una integración funciona hasta comprobarla.
- No simular conexiones ni ejecuciones que no se hayan realizado. Todo lo de arriba que dice "pendiente" o "bloqueado" es así, no se ha probado.
